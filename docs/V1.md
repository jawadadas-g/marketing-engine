# marketing-engine v1

As of 2026-09-21. What it does, what it does not, and what to build next.

## What it does

A standalone multi-tenant marketing engine. One Node service, one Postgres, one
HTTP API, no screens. A client — the marketplace first, but nothing here is
specific to it — provisions tenants, and each tenant:

- **Sends** SMS, WhatsApp, email and Telegram from one intent. The engine picks
  the channel when the caller does not, falls back when a send fails for good,
  and every send goes through `can_send` — suppression, then consent, then
  region-scoped sending windows in the contact's own local time. Provider
  credentials are encrypted at rest and every provider is one adapter file.
- **Finds** off-platform companies in a shared prospect pool fed by CSV imports,
  RFQ counterparties, API calls and an optional registrar lookup. One real
  company is one row whoever contributed it: strong identifiers (CR, VAT,
  domain) merge, weak ones (phone, email) link, and fuzzy name matching links
  only at 0.90 similarity on a name normalised for Arabic orthography and legal
  forms. Invites go out through the messaging module and the marketplace reports
  the signup back.
- **Discounts** with promocodes carrying rules, budgets and named funders. The
  checkout validates, reserves, settles and releases; every reservation is a
  hold on a ledger and every settlement a capture, and `reconcile` says whether
  the two agree.
- **Hears** about all of it. Every module appends to one append-only event log,
  and a tenant registers a webhook URL to receive those events, signed to the
  Standard Webhooks spec and retried five times over twelve hours.

- **Shows** what it is doing. A platform-scope read API under `/internal` gives
  an operator the queue, every tenant's traffic, why messages were blocked, the
  jobs that failed and a live event stream, without anyone opening a database
  client. `docs/DASHBOARD.md` is the guide for building the screen.

The whole of that is exercised end to end in CI by `npm run e2e`, which drives
the HTTP API alone.

## What it does not do

Not omissions to fix — decisions, listed so nobody looks for them.

- **No screens.** The client owns every interface.
- **No token issuing.** The marketplace mints tenant JWTs with the shared
  secret. The engine only verifies them.
- **No money movement.** The ledger records who owes what; settling between
  parties belongs to a finance system.
- **No campaigns, schedules or A/B tests.** One send is one call.
- **No real matching algorithm.** Discovery's `basic` finder is an AND of exact
  filters that scores everything 1.0. The interface, the endpoint and the
  `finder_runs` log are real so the algorithm can be swapped in as one file.
- **No inbound message handling.** Replies become `message.replied` events;
  acting on a STOP reply is not automatic.
- **No rate limiting, per-tenant API keys, or admin UI.**

## Its limits, honestly

Things that are true today and will bite somebody:

- **Three of the four channel adapters have never talked to their real API.**
  Taqnyat has sent live SMS. WhatsApp, SMTP and Telegram are proven only against
  fakes. Their first live send is their real test, and provider responses differ
  from provider docs — Taqnyat already proved that by reporting a sender problem
  as `"Number(s) is empty or incorrect"`.
- **The Wathq response mapping is unverified.** Its request contract is public;
  its response schema is not. The adapter is inert without `WATHQ_API_KEY` and
  keeps the whole payload in `raw`, but the fields it maps are guesses. One real
  call fixes it.
- **A merge cannot be undone through the API.** `merged_into` and the source
  rows make a merge legible, not reversible; undoing one is hand-written SQL.
- **Promocode rules and platform rules read in opposite directions.** A code's
  own document says when it *may* be used; a platform `promo_eligibility` row
  *denies* when it matches. Both are documented, neither is intuitive.
- **Idempotency has no single-flight lock.** Two genuinely concurrent first
  calls with the same key both run the handler. `reserve` is safe anyway because
  `orderRef` is unique and the code row is locked; other routes are not.
- **Category codes are uncontrolled strings.** `diesel`, `Diesel` and `ديزل` are
  three categories.
- **Discovery has one outcome signal and no ranking inputs.** Invites link back
  to the search that surfaced them, which is the raw material; there is no
  supplier-side profile, no quality measure on a company, and geography is one
  free-text city.

## When a tenant asks

From the architecture's "not in v1" list, each with the seam it already fits:

| Ask | Where it plugs in |
| --- | --- |
| A new channel or a second vendor | One new adapter file |
| A new company source | One new ingest connector calling `registry.upsert` |
| New sending or eligibility behaviour | A new rule kind, same evaluator |
| A new country | Region-scoped rule rows |
| The real discovery algorithm | A second `Finder`, one registry line, `FINDER` |
| A real ledger | The `Ledger` interface; the finance-engine stub is the shape |
| Better dedupe | A batch job proposing merges into the same registry |
| A rule-authoring UI | Swap json-logic for a rules engine that ships an editor; the JSON migrates |
| Analytics or a warehouse | Read the event log |
| A module outgrowing the monolith | It owns its tables and speaks through one interface; lift it out along that line |

If a request cannot be built through one of those, that is the signal to stop
and ask why, rather than to add a ninth mechanism.

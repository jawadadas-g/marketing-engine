# Brief 08 — Marketplace wiring

Read `CLAUDE.md` and `docs/ARCHITECTURE.md` first. This brief is roadmap step 8, the last of v1. Nothing new in the domain. Everything here is what a client needs to use the engine without touching its database: a way to get a tenant, a way to hear about events, a way to run it in production, and a document that says how.

## Goal
A fake marketplace client can, through the HTTP API alone: provision a tenant, configure a channel, import companies, search, invite, send, create a code, reserve and settle, and receive every resulting event on its own webhook URL, signed. That script is the done-when, and it runs in CI.

## Part A — housekeeping (first commit)
- Env validation at boot: one Zod schema for every variable the service reads (`DATABASE_URL`, `JWT_SECRET`, `CREDENTIALS_KEY`, `WEBHOOK_TOKEN`, `INTERNAL_TOKEN`, `PUBLIC_BASE_URL`, `MARKETPLACE_SIGNUP_URL`, `FINDER`, `LEDGER`, `PORT`, optional ones marked optional). Fail fast with the list of what is missing or malformed. Replace scattered `process.env` reads with the parsed object.
- Graceful shutdown: on SIGTERM/SIGINT stop accepting requests, `boss.stop({ graceful: true })`, close the pool, exit. In-flight sends finish or are retried by pg-boss; none are lost.

## Part B — the step

### Tenant provisioning
- `POST /internal/tenants` body `{ name, externalRef }` authenticated by `X-Internal-Token` → 201 `{ tenantId }`. Unique on `externalRef` (the marketplace's own company id); a repeat returns the existing tenant with 200. Emit `tenant.created` under that tenant.
- Tenant JWTs are minted by the marketplace with the shared `JWT_SECRET`: HS256, claims `{ sub: externalRef, tenant_id, exp }`. The engine never mints tokens. Document the claim shape and a 10-line example of minting in `docs/API.md`.

### Outbound webhooks
- Migration `0009_webhooks.sql`:
  - `webhook_endpoints (id uuid pk, tenant_id uuid null references tenants, url text not null, secret text not null, event_types text[] not null default '{}', active boolean not null default true, created_at)`. `tenant_id null` = the platform endpoint, which receives every tenant's events; created only through the internal route. Empty `event_types` = all. Tenant RLS as usual; the platform row is visible to no tenant. `secret` is generated by the engine (32 random bytes, base64url), returned once on creation, stored as-is (it is an HMAC key, not a credential we could avoid holding).
  - `webhook_deliveries (id bigserial pk, endpoint_id uuid not null, event_id bigint not null references events, attempt int not null default 0, status text not null check (status in ('pending','delivered','failed')), last_status_code int null, last_error text null, next_attempt_at timestamptz null, delivered_at timestamptz null, created_at)`, unique `(endpoint_id, event_id)`. Owner-only writes; tenant select through the endpoint's tenant.
- Fan-out: `events.emit()` enqueues one `webhook.fanout` job with the event id, inside the caller's transaction (the transactional `enqueue` from step 4), so an event that commits always fans out and one that rolls back never does. The fan-out worker (owner) loads the event, finds active endpoints matching `(tenant_id = event.tenant_id or tenant_id is null) and (event_types = '{}' or event.type = any(event_types))`, inserts a `pending` delivery per endpoint, and enqueues one `webhook.deliver` job per delivery.
- Delivery worker: `POST` the body below with a 10-second timeout; 2xx → `delivered`; anything else or a network error → increment `attempt`, set `next_attempt_at` by the schedule `1m, 5m, 30m, 2h, 12h` (five retries via pg-boss `retryLimit: 5` with explicit delays, not exponential guessing), then `failed`. Emit nothing for deliveries (no event about an event); log a warning on final failure.
- Body and headers follow the Standard Webhooks spec so any client library verifies it: JSON `{ id: "<event id>", type, tenantId, occurredAt, data: <payload> }`; headers `webhook-id` (the delivery id), `webhook-timestamp` (unix seconds), `webhook-signature: v1,<base64(HMAC-SHA256(secret, id + "." + timestamp + "." + body))>`. Also `Content-Type: application/json` and `User-Agent: marketing-engine/<version>`. Receivers reject timestamps older than 5 minutes; document that.
- Routes: `POST /v1/webhooks` body `{ url, eventTypes? }` → 201 with the secret (once). `GET /v1/webhooks`, `DELETE /v1/webhooks/:id`. `GET /v1/webhooks/:id/deliveries?status=` → the tenant's delivery log. `POST /v1/webhooks/:id/deliveries/:deliveryId/replay` → resets to `pending`, enqueues again, 202. `POST /internal/webhooks` (internal token) creates the platform endpoint. URL must be `https://` unless `PUBLIC_BASE_URL` itself is `http://` (local dev).

### Idempotency, tightened
`Idempotency-Key` becomes **required** (400 `idempotency_key_required`) on the money routes: `POST /v1/redemptions`, `/settle`, `/release`. Everywhere else it stays optional. Add the request-body hash to `idempotency_keys` (the step 1 review note): same key, different body → 422 `idempotency_key_reused`.

### Tracing and logs
- Structured JSON logs, one line per request (`method, path, status, tenantId, durationMs, requestId`) and one per job (`name, id, durationMs, ok`), written with `console.log(JSON.stringify(...))`. No logging library. `requestId` comes from `X-Request-Id` when present, else generated, and is echoed back.
- OpenTelemetry, three packages only: `@opentelemetry/api`, `@opentelemetry/sdk-node`, `@opentelemetry/exporter-trace-otlp-http`. Initialised in `src/otel.ts` only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; otherwise a no-op. Manual spans, not auto-instrumentation: one per HTTP request, one per pg-boss job, one per adapter `send`, one per ledger call, one per finder run. Trace id goes into the request log line. This is the whole observability story for v1.

### Production
- `Dockerfile`: multi-stage on `node:22-slim`, `npm ci` then `npm run build`, runtime image with only `dist` and production deps, non-root user, `HEALTHCHECK` on `/health`, `CMD` runs migrations then starts. `.dockerignore`.
- `docker-compose.prod.yml`: `engine` (built image, env from `.env.prod`, restart always), `postgres:16` on a named volume, and `backup`: a tiny `postgres:16` container with a cron loop that runs `pg_dump --schema=marketing --schema=pgboss` nightly to a `backups` volume with 14-day rotation. A README section on restoring from one of those dumps, tested once by hand and the command pasted.
- `/health` gains `{ ok, db, boss: <queue state>, version }`.

### `docs/API.md`
Hand-written, no generator. One section per route group: tenants, channels, templates, messages, consent, suppression, rules, companies, discovery, invites, promocodes, redemptions, webhooks, internal, public (`/i/:token`, `/unsubscribe/:token`, `/webhooks/:provider/:token`). For each route: method, path, auth (tenant JWT / internal token / none), request body shape, response shape, error codes. Then four sequence descriptions the marketplace has to implement: the invite handshake, the checkout handshake, receiving webhooks (with the verification snippet), and the two provider webhook registrations. Conventions in bold at the top: minor units, basis points, E.164, `Idempotency-Key`.

### End-to-end script (`scripts/e2e.ts`, `npm run e2e`)
Starts the built service against `DATABASE_URL_TEST`, starts a local HTTP listener as the "marketplace", and as a client does, in order: provision a tenant (internal) → mint a JWT → register the listener as a tenant webhook → configure the fake SMS channel → save a template → grant consent for a phone → import a 3-row CSV with profiles → search `{ buys: [diesel] }` and get results → invite the first result (fake channel) → follow `/i/:token` and call the internal accept → search again and see it gone → create a 10% code → validate → reserve with an `Idempotency-Key` → settle → `reconcile` agrees → send one transactional message and `processSend` it. Then assert the listener received, signed and verifiable, at least these event types: `tenant.created`, `channel.configured`, `consent.granted`, `company.created`, `invite.sent`, `invite.accepted`, `promo.reserved`, `promo.settled`, `message.queued`, `message.sent`. Exit non-zero on any miss. Runs in CI after the unit tests.

### Tests, CI (`test/wiring.test.ts`)
1. Boot with a missing `CREDENTIALS_KEY` → process exits with a message naming it.
2. `POST /internal/tenants` twice with the same `externalRef` → one tenant, 201 then 200; wrong token → 401.
3. An event emitted inside a transaction that rolls back produces no `webhook_deliveries` row; one that commits produces one per matching endpoint, none for a non-matching `event_types` filter, and one for the platform endpoint.
4. Delivery signature verifies with the Standard Webhooks algorithm against the returned secret; a tampered body fails verification.
5. A listener returning 500 → attempt 1, `pending`, `next_attempt_at` set; after the fifth failure → `failed`; replay → `pending` again and delivered when the listener returns 200.
6. `POST /v1/redemptions` without `Idempotency-Key` → 400; same key with a different body → 422; same key and body → identical replay.
7. Tenant B cannot see A's endpoints or deliveries; no tenant can see the platform endpoint.
8. `/health` reports `db: true` and a queue state.

### Done when
CI runs unit tests then `npm run e2e`, both green; the Docker image builds; `docs/API.md` covers every route in `src/api/routes`; a restore from a `pg_dump` produced by the backup container has been done once by hand and the commands are in the README. Update the roadmap in `docs/ARCHITECTURE.md`: all eight rows done, with dates.

## Do not
- Add a webhook service, a logging library, a metrics library, or auto-instrumentation. Three OpenTelemetry packages is the ceiling.
- Generate the API doc from code; hand-write it.
- Add rate limiting, API keys per tenant, or an admin UI. Tenants authenticate with marketplace-minted JWTs, full stop.
- Emit events about webhook deliveries.
